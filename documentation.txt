
# Company OS

> An internal company knowledge and operating system that centralizes organizational data, documents, and knowledge retrieval into a single platform.

Company OS is designed to act as a **company brain** — connecting company data, documents, organizational information, and AI-powered retrieval through a unified application.

The system is being developed as a modular platform where individual capabilities are built as independent services and then wired together into a larger workflow.

---

# 1. Overview

Company OS provides a centralized platform for:

- Company information
- Organizational structures
- Users and workspaces
- Documents
- Document storage
- Document extraction
- Document chunking
- Semantic embeddings
- Knowledge retrieval
- AI-powered question answering
- Source citations
- Authentication and authorization

The core philosophy is:

> **Build individual capabilities as small, independent tools, then wire them together into a complete company operating system.**

The initial implementation intentionally avoids introducing unnecessary infrastructure such as Elasticsearch, OpenSearch, Vespa, Kafka, Kubernetes, or Airflow.

PostgreSQL is used as the primary database, with `pgvector` providing vector search capabilities.

# 10. MinIO Object Storage

MinIO is used as the document object-storage layer.

Instead of storing PDF files directly inside PostgreSQL, PostgreSQL stores metadata while MinIO stores the actual file.

Architecture:

```text
PDF
 |
 v
MinIO
 |
 +-- documents/
       |
       +-- file-uuid-1.pdf
       +-- file-uuid-2.pdf
       +-- ...
```

The database stores information such as:

```text
document_id
filename
file_type
storage_key
workspace_id
```

Example storage key:

```text
documents/<uuid>.pdf
```

This separation keeps database records lightweight while allowing object storage to handle the actual files.

# 17. Document Ingestion Pipeline

The document ingestion system is built as separate components.

Current architecture:

```text
                    Upload
                       |
                       v
                 FastAPI API
                       |
                       v
                    MinIO
                       |
                       v
              Document Metadata
                  PostgreSQL
                       |
                       v
               Text Extraction
                       |
                       v
                   Chunking
                       |
                       v
                 Embeddings
                       |
                       v
                 PostgreSQL
                   pgvector
```

---

## Step 1 — Upload

A user uploads a document through the frontend.

The backend receives the file.

---

## Step 2 — MinIO

The actual document is stored in MinIO.

Example:

```text
documents/
└── <uuid>.pdf
```

---

## Step 3 — Document Record

PostgreSQL stores metadata about the document.

Typical information:

```text
id
filename
file_type
storage_key
workspace_id
created_at
```

---

## Step 4 — Text Extraction

The backend retrieves the document from MinIO and extracts readable text.

For PDFs, the extracted text is passed to the ingestion pipeline.

---

## Step 5 — Chunking

Large documents are split into smaller chunks.

For example:

```text
Document
   |
   +-- Chunk 0
   +-- Chunk 1
   +-- Chunk 2
   +-- Chunk 3
```

The database stores:

```text
document_id
chunk_index
content
created_at
```

Page metadata can also be associated with chunks to support source citations.

---

# 18. Embeddings

Each document chunk is converted into a numerical vector.

Current embedding configuration:

```text
Embedding dimension: 384
```

Conceptually:

```text
Text Chunk
    |
    v
Embedding Model
    |
    v
[0.0208, 0.0149, 0.0332, ...]
    |
    v
384 dimensions
    |
    v
pgvector
```

The embedding is stored in PostgreSQL using:

```text
vector(384)
```

The same embedding model must be used for:

```text
Document chunks
```

and later for:

```text
User search queries
```

Otherwise vector similarity will not be meaningful.

# 19. Current Retrieval Architecture

The retrieval layer is being developed using a hybrid-search approach.

We intentionally do not introduce another dedicated search database in Phase 1.

We are using:

```text
PostgreSQL
│
├── Relational data
├── Metadata
├── Keyword retrieval
└── pgvector semantic retrieval
```

Hybrid search will combine:

```text
                  User Query
                      |
          +-----------+-----------+
          |                       |
          v                       v
   Keyword Search          Vector Search
   PostgreSQL              pgvector
          |                       |
          +-----------+-----------+
                      |
                      v
                 Result Fusion
                      |
                      v
                   Top-K
                      |
                      v
            Document + Page Metadata
                      |
                      v
                    RAG
```

The search result should eventually contain enough information for citations:

```json
{
  "document_id": 2,
  "chunk_id": 3,
  "filename": "document.pdf",
  "content": "Relevant text...",
  "page_number": 4,
  "score": 0.91
}
```

```sql

SELECT
    id,
```


First check:

```powershell
alembic current
```

Then:

```powershell
alembic history
```

If port `8000` is already being used:

```powershell

```

If port `3000` is being used, Next.js will normally offer another available port.

---

## Frontend cannot reach backend

Verify the backend is running:

```text
http://127.0.0.1:8000/docs
```

Then verify the frontend API configuration points to the correct backend URL.

---

## Registration does not work

Check:

```text

```

```text
http://127.0.0.1:8000/docs
```

Then verify PostgreSQL:


and:

```sql

```

## Embedding model download is slow

The embedding model may be downloaded the first time it is used.

```text

```

# Development Principle

Company OS follows a simple engineering principle:

> **Break the system into sub-tools → build each tool independently → test each tool → wire the tools together → stack them into the complete system.**

For example:

```text
Storage
   ↓
Ingestion
   ↓
Extraction
   ↓
Chunking
   ↓
Embeddings
   ↓
Vector Storage
   ↓
Keyword Search
   ↓
Vector Search
   ↓
Hybrid Search
   ↓
RAG
   ↓
LLM
   ↓
Citations
```

This keeps the architecture modular, testable, and easier to scale.
